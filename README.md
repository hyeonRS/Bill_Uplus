## URECA 3기 종합 프로젝트 1조

# 📊 대용량 통신 요금 명세서 및 알림 발송 시스템

## 1. 프로젝트 개요
본 프로젝트는 통신사의 대용량 사용자 및 이용 내역을 기반으로 정산하고, 생성된 청구결과를 고객에게 이메일/SMS 등 다양한 채널을 통해 메시지로 발송하는 시스템입니다.

월 수백만 건 이상의 요금 데이터와 대량의 메시지 발송 환경을 가정하여 설계하였으며
운영자는 백오피스 대시보드에서 청구서와 배치 실행 결과, 메시지 상태 및 발송 이력을 조회할 수 있습니다. 또한 템플릿과 발송 정책을 관리하며 정산부터 알림발송까지의 흐름을 추적할 수 있습니다.

<br>

---
## 2. 프로젝트 배경 및 목적
통신 서비스에서는 매월 대규모 요금 데이터가 생성되며,  
요금 고지·연체 알림·청구 안내 등 다양한 고객 알림이 필수적으로 발생합니다.

본 프로젝트는 다음과 같은 문제를 해결하는 데 목적이 있습니다.
- 대량 요금 데이터의 안정적인 정산 처리
- 대규모 메시지 발송 시 장애 격리 및 재처리
- 발송 성공/실패 이력 관리 및 중복 발송 방지
- 실무에서 사용되는 메시지 기반 아키텍처 경험


## 4. 주요 기능

### 4.1 요금 정산 및 명세서 생성
- 가상 고객 100만 명, 청구 이력 500만 건 데이터 생성
- 월별 Batch 작업으로 요금 정산 수행
- 요금 명세 데이터를 데이터베이스에 저장

### 4.2 메시지 발송 요청 처리
- 요금 정산 완료 시 Kafka 이벤트 발행
- 메시지 발송은 비동기 방식으로 처리
- 이메일, SMS 발송 채널 분리 설계

### 4.3 이메일 / SMS 발송
- 이메일, SMS 발송 기능 구현 (Mock 기반)
- 발송 실패 시 자동 재시도 로직 적용
- 이메일 발송 실패 시 최대 1초 지연 후 재시도
- SMS는 실패하더라도 재시도 없이 종료 가능

### 4.4 발송 이력 및 상태 관리
- 메시지 단위 발송 상태 관리
  - ATTEMPTING / SUCCESS / FAIL
- 발송 시도 횟수 기록
- 외부 발송 시스템 메시지 ID 저장
- 중복 발송 방지 로직 구현

### 4.5 확장 기능 
- 이메일, SMS 외 Push 메시지 확장 가능 구조
- 특정 시간대 예약 발송 기능
- 발송 실패 메시지 재처리(Replay) 기능

## 6. 처리 흐름

### 6.1 핵심 처리 흐름

1. 운영자가 관리자 화면 또는 API에서 정산 대상과 청구 정보를 확인
2. Quartz 스케줄 또는 수동 요청으로 Spring Batch Job을 실행
3. 배치가 요금과 할인을 계산하고 청구서, 청구 상세, 정산 이력을 MySQL에 저장
4. 청구 결과를 바탕으로 발송 대상 메시지를 Outbox에 저장
5. 메시지 서버가 Outbox를 조회해 Kafka 이벤트를 발행
6. Kafka 소비자가 방해 금지 시간, 템플릿, 재시도 정책을 적용해 Email·SMS·Push 채널로 발송
7. 발송 상태와 시도 이력을 저장하며, 운영자는 대시보드와 관리 API에서 결과를 조회하고 필요하면 템플릿을 수정

<br>


### 6.2 알림 발송 아키텍처 및 이벤트 흐름

- 정산 배치는 발송 대상 메시지를 DB에 저장하고, 메시지 서버는 이를 Kafka를 통해 비동기로 처리합니다.

```bash
[ billing-batch / Spring Batch ]
        │  청구서·청구 상세 생성
        └─ Message Outbox 저장 (MySQL)
                    │
                    ▼
[ message / MessageOutboxPoller ]
        │  발송 가능한 PENDING·DND_HOLD 메시지 조회
        │  5초 간격, 한 번에 최대 100건
        ▼
[ Kafka Topic: message.send.request ]
        │
        ▼
[ MessageSendConsumer → MessageDispatcher ]
        ├─ Step 1: 방해 금지 시간(DND) 확인
        │    해당 시간대라면 발송 가능 시각으로 연기
        │
        ├─ Step 2: 청구 정보로 템플릿 payload 생성
        │
        └─ Step 3: Email / SMS / Push 채널 발송
             ├─ 성공 → Message 상태 및 MessageAttempt 기록
             └─ 실패 → 재시도 정책 적용
                        재시도 소진 시 다음 채널 메시지 생성 또는 실패 처리

[ billing / 관리자 화면·REST API ]
  ├─ 청구서 및 배치 실행·조회
  ├─ 메시지 상태와 발송 이력 조회
  └─ 템플릿·방해 금지 시간·재시도 정책 관리
```

## 7. 기대 효과
### 정산·발송 운영 효율 향상
- 정산 배치 실행부터 청구 결과 조회, 메시지 발송 이력 확인까지 관리자 시스템에서 이어서 처리할 수 있음

### 대용량 정산 처리 현황 파악
- 배치 실행 결과와 청구서 생성 상태를 조회해 정산 진행 상황과 처리 결과를 확인할 수 있음

### 메시지 발송 이력 추적
- 메시지 상태와 발송 시도 기록을 통해 실패 여부를 확인하고 재시도나 후속 조치에 필요한 정보를 찾을 수 있음

### 반복 업무 감소
- 정산 스케줄링, 메시지 비동기 발송, 템플릿 관리를 통해 정기적으로 수행하는 운영 작업을 줄일 수 있음
